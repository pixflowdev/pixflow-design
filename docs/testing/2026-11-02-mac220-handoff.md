## Targeted acceptance

1. Update the existing isolated plugins in place. Record the active site, chat counts and relevant settings before and after testing. Use a new disposable page and translation job for writes. Never use customer pages or sign out a provider.
2. With Bridge unavailable, use the configured API to translate one fixture into two languages. Check automatic publication, one saved manual correction after update, anonymous translated pages and the frontend picker with Bridge still offline. Check that Free alone does not expose translation management.
3. With the paired Bridge, run a small WordPress translation through Codex and Claude, recording actual selected model, route and completion. Check direct connection and the installed v1.0.3 extension using only the test site's consent. With the extension selected, verify the actual UI route and rule out direct fallback.
4. Overlap onboarding or settings Local CLI discovery with a floating panel readiness check and a Workspace refresh. While a scan is running verify that the same site's health and the status label stay connected. Stop the isolated worker, check that it shows unavailable, then restore it and verify recovery. Confirm both staging and default health independently.
5. Sanity-check the new chat stream and citations on a small read-only prompt. On a fresh fixture, check Continue without AI, licence Retry on a simulated service outage and a redacted About diagnostics export with WordPress debugging off. Avoid destructive onboarding reset or licence manipulation on an established site. Record skips explicitly. Prior broad builder/SEO, usage and permissions matrices are supporting evidence and need not be repeated.
6. With no active translations, the Design tools shortcut has no dot. In a disposable page with an active translation, edit the source and compare the shortcut dot with the Workspace rail. Open Translations via the shortcut, update the page, then reopen the menu to confirm both dots clear. Confirm the shortcut stays hidden for a user without translation management permission.

## Build the two production DMGs

After the targeted checks pass and the paired integration CI is green, use the established portable 2.1.4 Mac recipe with version **2.2.0**. Run each build in its own architecture-specific output namespace with the corresponding Node/Electron and native SQLite bindings. On Apple Silicon use x64 Node under Rosetta for Intel when physical Intel hardware is unavailable. Verify `node -p process.arch` in each shell. Record which hardware ran each test.

From the pinned Core checkout, stage its native helper with:

```sh
pnpm exec tsx tools/pixflow-design-bridge/native-messaging/store-build.ts hbnbiboohlelmngadeolikeejamjlbkh
export PIXFLOW_DESIGN_NATIVE_PAYLOAD_DIR="$PWD/.tmp/chrome-store/native"
```

Use the product identity, icon, update URL and tray settings from `scripts/build-pixflow-design-bridge-mac-installers.mjs`, following the previously verified [Mac production receipt](evidence/mac214-usage-recovery/README.md). Use `tools-pack mac build --to dmg --portable --app-version 2.2.0` with the product environment and architecture-specific namespace from that recipe. The wrapper's `--arm64` and `--x64` arguments **import existing files**. Build each architecture before invoking the import. Create exactly one extension-ready DMG per architecture, with direct connections supported. The installed Store helper remains v1.0.3.

Run `hdiutil verify`, mount and verify the product version, portable configuration, host ID, Mach-O architectures, SQLite binding and actual runtime health for each exact DMG. Check signatures and report the real signing identity, Gatekeeper and notarisation results. Prior release artifacts were ad-hoc signed and not notarised; do not claim stronger signing than the new artifacts have.
